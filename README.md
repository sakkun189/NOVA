# SaaS販売管理システム ベンダコントロールプレーン モック画面定義

## 1. このドキュメントの目的

このドキュメントは、SaaS版の販売管理システムにおける `ベンダコントロールプレーン` のモック画面を作成するための定義書である。

今回モック画面を作成する対象は、以下 3 領域のうち `ベンダコントロールプレーン` のみとする。

- ベンダコントロールプレーン
- テナントコントロールプレーン
- アプリコントロールプレーン

本ドキュメントでは、だれが使う画面なのか、どのような管理機能が必要なのか、どのような画面を用意すべきかを整理する。

## 2. 今回の対象範囲

### 対象

SaaS型販売管理システムを導入した企業側の `システム運用者` のみが参照、操作できる管理機能、管理画面を対象とする。

ここでいうベンダコントロールプレーンは、各導入企業の運用管理者が、自社テナントの運用、利用者管理、監視運用を行うための管理領域を指す。

### 対象外

以下は今回のモック画面作成対象外とする。

- 実際の販売管理業務を行う業務画面
- 一般利用者が利用するアプリケーション画面
- ベンダ内部のSaaS提供者向け運用画面
- テナントコントロールプレーン全般
- アプリコントロールプレーン全般

## 3. 想定利用者

今回のモック画面の主利用者は、販売管理システムを導入した企業側の `システム運用者` である。

| 利用者 | 役割 | 主な利用目的 |
| --- | --- | --- |
| システム運用者 | 導入企業内の運用管理担当 | テナント設定確認、エンドユーザ管理、監視、ログ確認 |

必要に応じて、将来的には権限差分を持つ以下の利用者を追加する余地はある。

- システム運用責任者
- 監査担当者
- セキュリティ管理者

ただし、初期モックでは `システム運用者` を単一の主要利用者として扱う。

## 4. 必要な管理機能

今回必要な管理機能は、以下の 3 分類とする。

### 4.1 テナント管理

システム運用者が、自社テナントに関する基本情報や設定情報を確認、更新するための機能。

含める機能は以下。

- テナント照会
- テナント編集

### 4.2 エンドユーザ管理

システム運用者が、自社内で利用するエンドユーザのアカウントを管理するための機能。

含める機能は以下。

- エンドユーザ登録
- パスワードリセット

将来的には以下の追加余地がある。

- エンドユーザ一覧
- エンドユーザ詳細
- エンドユーザ編集
- アカウント無効化
- 権限、ロール変更

ただし、初期モックではユーザ管理の中心操作を `登録` と `パスワードリセット` に置く。

### 4.3 監視、運用管理

システム運用者が、利用状況や異常を把握し、運用監視を行うための機能。

含める機能は以下。

- 操作ログ
- ログインログ
- エラー監視

## 5. モック画面として必要な画面

初期モックでは、以下の画面を定義対象とする。

| 画面名 | 管理機能 | 画面の目的 | 主な操作 |
| --- | --- | --- | --- |
| ログイン画面 | 共通 | システム運用者の認証 | ログイン |
| ダッシュボード画面 | 共通 | 管理機能への入口、監視状況の要約確認 | 状況確認、各画面への遷移 |
| テナント照会画面 | テナント管理 | テナント情報の確認 | 情報参照、編集画面遷移 |
| テナント編集画面 | テナント管理 | テナント情報の更新 | 入力、保存 |
| エンドユーザ登録画面 | エンドユーザ管理 | 新規エンドユーザ登録 | 入力、登録 |
| パスワードリセット画面 | エンドユーザ管理 | 対象ユーザのパスワード再設定 | 対象指定、リセット実行 |
| 操作ログ画面 | 監視、運用管理 | 操作履歴の確認 | 検索、絞り込み、詳細確認 |
| ログインログ画面 | 監視、運用管理 | ログイン履歴の確認 | 検索、絞り込み、詳細確認 |
| エラー監視画面 | 監視、運用管理 | システム異常の確認 | 一覧確認、重要度確認、詳細確認 |

## 6. 各画面で定義すべき内容

モック画面ごとに、最低限以下を定義する。

- 画面名
- 利用者
- 画面の目的
- 表示する主要情報
- 操作できる内容
- 遷移先画面

画面種別ごとには、以下も定義する。

### 一覧、参照系画面

- 検索条件
- 表示項目
- ソート有無
- フィルタ条件
- 詳細遷移有無

### 登録、編集系画面

- 入力項目
- 必須項目
- 入力チェック
- 保存時の挙動
- 完了後の遷移

### 監視系画面

- 表示対象期間
- 重要度区分
- 異常状態の見せ方
- 詳細確認方法

## 7. 画面設計の方針

今回のモック画面では、以下を重視する。

- システム運用者が必要な管理機能にすぐ到達できること
- 参照系画面と操作系画面の役割が明確であること
- テナント管理、ユーザ管理、監視運用の 3 領域が整理されていること
- SaaSの管理画面として違和感のない情報設計になっていること

見た目の装飾よりも、管理機能の整理、画面構成、導線の明確化を優先する。

2. ダッシュボード

- エラー監視

## 9. 画面別の要点

### ログイン画面

- システム運用者のみが利用する管理画面入口
- 一般利用者向け画面とは明確に分離する

### ダッシュボード画面

- 主要管理機能への入口となる
- エラー件数、直近ログイン状況、運用上の注意事項などを要約表示する想定

### テナント照会画面

- テナント名、契約情報、利用状態、基本設定などを確認できる想定
- 契約情報には、ベンダとの契約日とテナント利用開始日を含める
- 利用状態には、アプリ `NOVA`、`GOM` ごとの利用有無や利用状況を含める

### テナント編集画面

- テナント基本設定の変更を行う想定
- 編集可能項目と参照専用項目の分離が必要
- 契約情報やアプリ利用状況のうち、どこまで編集可能とするかを明確化する必要がある

### エンドユーザ登録画面

- 新規ユーザ作成に必要な最小限の入力項目を整理する
- 必須項目は `メールアドレス`、`名前`、`部署等の所属` とする
- 登録後の通知や初期パスワード扱いは今後要件確認が必要

### パスワードリセット画面

- 対象ユーザを誤らず指定できることが重要
- 実行前確認や完了メッセージの設計が必要
- モックでは、管理者が対象ユーザを指定してリセット実行し、再設定案内をユーザへ通知する方式を前提とする

### 操作ログ画面

- だれが、いつ、何をしたかを追跡できる必要がある
- 監査観点を意識した見せ方が必要
- モックでは、ログイン、ログアウト、テナント情報更新、エンドユーザ登録、パスワードリセット、通知配信などの管理操作を記録対象とする

### ログインログ画面

- 成功、失敗を含むログイン履歴を確認できる想定
- 異常ログインの兆候に気づけることが重要
- 表示属性は、`だれが`、`いつ`、`どのアプリに` ログインしたかを最低限含める

### エラー監視画面

- 発生中、未対応、解消済みなどの状態が把握できること
- 重要度や発生日時で優先度判断できることが重要
- モックでは、重大度を `Critical`、`Warning`、`Info` の 3 段階で扱い、アプリ単位で状況把握できる粒度を前提とする

### 通知機能

- ベンダ側の新機能リリース時などに、テナント管理者へ通知できることを想定する
- ダッシュボードで通知概要を確認でき、必要に応じて通知一覧や詳細に遷移できる構成が望ましい

## 11. 追加検討候補画面

初期モック対象外ではあるが、導入企業側のシステム運用者が実運用で必要としやすい追加候補画面は以下。

### 11.1 エンドユーザ一覧画面

画面の目的は、登録済みユーザを一覧で把握し、状態確認や個別操作の入口にすること。

表示項目は以下。

- ユーザID
- 名前
- メールアドレス
- 部署、所属
- 役職
- 利用アプリ
- ロール
- アカウント状態
- 最終ログイン日時
- 登録日
- パスワードリセット最終実施日時

検索、絞り込み条件は以下。

- 名前
- メールアドレス
- 部署
- 利用アプリ
- ロール
- 有効、無効
- 最終ログイン有無

### 11.2 エンドユーザ詳細画面

画面の目的は、1ユーザ単位で利用状況、権限、運用履歴を確認すること。

表示項目は以下。

- 基本情報
- 割当ロール
- 権限概要
- 利用アプリ
- アカウント状態
- 最終ログイン情報
- パスワードリセット履歴
- 操作履歴の抜粋
- 作成者、更新者
- 登録日時、更新日時

### 11.3 ユーザ状態変更画面またはモーダル

画面の目的は、無効化、再有効化、ロール変更などの日常運用操作を行うこと。

表示項目は以下。

- 対象ユーザ名
- 現在状態
- 現在ロール
- 変更後状態
- 変更後ロール
- 実施理由
- 実行確認

### 11.4 ロール割当管理画面

画面の目的は、RBAC定義を見るだけでなく、だれにどのロールを付与するかを管理すること。

表示項目は以下。

- ユーザ名
- 所属
- 利用アプリ
- 現在ロール
- 変更候補ロール
- ロール説明
- 主要権限サマリ

検討事項は以下。

- ロール変更を即時反映するか
- 承認フローを必要とするか

### 11.5 契約、ライセンス利用状況画面

画面の目的は、契約内容と消費状況を一画面で把握すること。

表示項目は以下。

- 契約プラン
- 契約開始日
- 更新期限
- 契約ステータス
- ユーザ登録上限数
- 現在登録数
- 残数
- アプリ別利用数
- オプション契約一覧
- オプションごとの利用開始状況
- 超過見込みアラート

### 11.6 通知一覧画面

画面の目的は、ベンダ通知を一覧で確認し、見落としを防ぐこと。

表示項目は以下。

- 通知タイトル
- 通知種別
- 対象アプリ
- 配信日時
- 重要度
- 既読、未読
- 通知概要
- 詳細確認導線
- 対応要否

フィルタ条件は以下。

- 未読のみ
- リリース
- メンテナンス
- 障害
- セキュリティ

### 11.7 通知詳細画面

画面の目的は、新機能や障害連絡の詳細を確認すること。

表示項目は以下。

- タイトル
- 配信日時
- 対象アプリ
- 本文
- 影響範囲
- 対応期限
- 関連リンク
- 設定ウィザード開始導線
- 既読化状況

### 11.8 障害、メンテナンス状況画面

画面の目的は、自社に関係するベンダ起因の障害や計画停止を把握すること。

表示項目は以下。

- 事象ID
- 種別
- 対象アプリ
- 発生日時
- 現在ステータス
- 影響範囲
- 回避策
- 復旧見込み
- 更新日時

区別すべき観点は以下。

- 自社のエラー監視
- ベンダ全体の障害情報

### 11.9 監査レポート画面

画面の目的は、操作ログやログインログを監査向けに整理して出力すること。

表示項目は以下。

- 集計対象期間
- 対象ログ種別
- 操作者
- 対象機能
- 実行結果
- 出力形式
- 出力実行履歴

### 11.10 セキュリティ状況画面

画面の目的は、運用者が気にするべきリスクをまとめて確認すること。

表示項目は以下。

- 長期未ログインユーザ数
- ログイン失敗多発ユーザ数
- パスワードリセット多発件数
- 管理者ロール保有者数
- MFA対象数、設定状況
- 不審アクセス兆候
- 推奨対応事項

### 11.11 リリース機能設定画面

画面の目的は、新機能追加時に、対象部門や対象ユーザへの適用を設定すること。

表示項目は以下。

- 機能名
- 提供開始日
- 利用対象部門
- 利用対象ロール
- 有効化状態
- 初期設定状況
- 関連通知

## 12. 優先度の高い追加候補

優先度が高い候補は以下。

1. エンドユーザ一覧
2. 契約、ライセンス利用状況
3. 通知一覧
4. ロール割当管理
5. 障害、メンテナンス状況

## 13. 画面追加時の考え方

- ダッシュボード
- エンドユーザ一覧
- 通知一覧

問題発生時に見る画面は以下。

- ログインログ
- エラー監視
- 障害、メンテナンス状況

月次や棚卸しで見る画面は以下。

- 契約、ライセンス利用状況
- 監査レポート
- ロール割当管理

## 14. 未確定事項

モック画面作成前に、今後詰めるべき点は以下。

- ベンダコントロールプレーンという名称と、実際の権限範囲の最終定義
- システム運用者の権限分割有無

現時点で確定した内容は以下。

| 項目 | 現時点の整理 |
| --- | --- |
| テナント照会、編集で扱う具体的な項目 | ベンダとの契約日、テナント利用開始日などの契約情報、およびアプリ `NOVA`、`GOM` の利用状況を扱う |
| エンドユーザ登録時の必須項目 | `メールアドレス`、`名前`、`部署等の所属` |
| パスワードリセット方式 | 詳細要件は未確定だが、モックでは管理者実行型の標準的なリセット方式を仮置きする |
| 操作ログに記録するイベント範囲 | 詳細要件は未確定だが、主要な管理操作を対象にする前提でモック化する |
| ログインログに表示する属性 | `だれが`、`いつ`、`どのアプリに` ログインしたか |
| エラー監視の粒度 | 詳細要件は未確定だが、重大度 3 段階かつアプリ単位で把握できる粒度を仮置きする |
| 通知機能の有無 | あり。ベンダ側の新機能リリース時などにテナント管理者へ通知したい |
